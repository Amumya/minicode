## 二、三个值得单独说的决定

### 1. 为什么只给 todo 加"依赖"，不搬那 6 个工具

我算过账：现有 6 个工具的 schema 是 **1532 字符 ≈ 510 token/轮**。再加 6 个约 **+800 token/轮**，
9 步任务光工具定义就多发 **~7200 token** —— 而我们实测一个压缩后的任务**总输入只有 4185 token**。
**工具定义比任务本身还贵。**

而且 claim/owner 是为多代理抢活设计的（参考项目紧接着就是 s13 agent teams），
我们只有一个子代理、跑完就返回、不共享任务板，**这套语义现在没有消费者**。

所以：日常规划用 `todo_write`（+依赖+环检测），真需要"跨 run、有归属、有解锁报告"时开 `--tasks`。
两个工具并存，各管一段，这也是参考项目自己的演进路径。

### 2. 前端八项里，只有一项需要改后端

计划、花费、续跑、筛选、参数、压缩效果 —— **全部来自事件流**：
`todo_write` 的 `args.todos` 就是完整计划；`model_call.usage` 累加就是花费；
`compact.saved_chars` 就是压缩效果；`POST /runs/{id}/resume` 早就有了。

唯一例外是任务看板：`create_task` 的 ID 只在工具**结果**里出现，从事件反推容易错，
所以加了 `GET /runs/{id}/tasks` 直接读任务目录。

**这是当初"事件流"这个设计的红利：要加展示面，后端一行没动。**

### 3. 桌面壳为什么不选 Electron

| 方案 | 结论 |
|---|---|
| Electron | 要下 ~100MB，这台机器代理不稳 |
| Tauri | 要 Rust，没装 |
| pywebview | 要 pythonnet，多一层原生依赖 |
| **`msedge --app`** | **零新依赖**，Edge 和 WebView2 都已装 |

还有一个必须踩的坑：**一定要给独立 `--user-data-dir`**。不给的话 Edge 会把窗口交给已有进程、
自己立刻退出，`proc.wait()` 马上返回 —— 我们会以为窗口关了而把服务关掉，**而窗口还开着**。

另外刻意没做成"纯桌面应用"：这个项目的一部分价值是**可被检查**（HTTP + SSE + `curl`）。
桌面壳只是多一个入口，uvicorn 还在。

## 二点五、把沙箱消融干净重测了一遍（n=4）

上一轮那批数据因为判定器 bug 和基准污染作废了，这次在隔离好的环境里重跑：

| 指标 | 只有 bash | 加文件工具 |
|---|---|---|
| 通过率 | **23/24（96%）** | **24/24（100%）** |
| 平均步数 | 7.1 | 7.2 |
| 平均输出 token | **1912** | **2336（+22%）** |
| 工具调用失败率 | 10% | **7%** |
| 想改测试被拦 | 0 | **2 次** |

唯一有区分度的任务是 `t6_spec`（bash 3/4，文件工具 4/4）—— 需要反复读 SPEC 和大文件。
另外 `t3_median` 和 `t4_config` 用文件工具明显更省（−58% / −38% token）。

**结论比之前更保守也更站得住**：文件工具救回了一个失败案例、失败率更低，
但整体多花 22% token。样本 24 次/组，够说方向，不够说"提升几个百分点"。
