# 取舍与证据

每做一个决定记一条：**其他方案是什么、为什么不用、实际测出来多少**。

写这个是为了以后翻的时候能想起来当时为什么这么选，别靠回忆。
反过来也一样：没有测过的，这里就写"还没测"。

## D1 工具返回值保留退出码

| | |
|---|---|
| 做法 | `ToolResult` 里带 `exit_code`，给模型看的内容前面加 `[exit=N]` |
| 别的方案 | 把 stdout 和 stderr 拼成一段文本返回（最常见） |
| 为什么不用 | 拼文本会把失败信息抹平。命令报错了，模型看到一大段输出，不知道它失败了，会接着往下瞎猜 |
| 测出来的 | `tests/test_tools.py::test_failure_keeps_exit_code` 守住这条；真实任务里 `tool_call` 事件记到 `exit_code=0`、`failed=false` |
| 一个真实例子 | 让它数 `src/minicode/tools` 下几个 py 文件。第一步它写了 `ls src/minicode/tools/*.py 2>/dev/null \| wc -l`，在 PowerShell 下 `wc` 不存在、`2>/dev/null` 也不合法，退出码 1。**因为看到了 exit=1，它第二步换成 `(Get-ChildItem ... -Filter *.py).Count`，然后答对 3** |
| 如果丢掉退出码会怎样 | 模型看到的是一段空输出，很可能直接答"0 个文件"。所以这个决定不是洁癖，它直接改变了行为 |
| 能讲的点 | 失败率能不能算，取决于退出码有没有留下来。这是个"看起来无所谓、实际决定能不能评测"的细节 |

## D2 权限用分词加参数判定，不用子串黑名单

| | |
|---|---|
| 做法 | 先把命令按 `;` `&&` `\|\|` `\|` 切成链，再 `shlex` 分词拿到程序名和参数，按参数语义判 |
| 别的方案 | `if "rm -rf" in cmd` 这类子串匹配 |
| 为什么不用 | 见下面的实测。子串匹配同时会漏和会误伤 |
| 测出来的 | 16 条危险 + 12 条正常：拦截率 **56.2% → 100%**，误报率 **33.3% → 0%**。结果在 `eval/runs/perm_*.json` |
| 漏掉的典型 | `rm  -rf   /`（多空格）、`rm -fr /`（参数顺序）、`git reset --hard`、`git clean -fdx`、`chmod -R 777 /`、`echo hi > /etc/passwd`、`:(){ :\|:& };:` |
| 误伤的典型 | `echo "rm -rf /"`、`grep -r "rm -rf" .`、`rm -rf ./build`、`echo 'shutdown'` |
| 还没做的 | 用例是我自己写的，不是从真实操作日志里抽的。这个对比能说明两种方法差很多，不能说明结构化判定在真实环境也是 100% |

## D3 Windows 上用 PowerShell 当 shell

| | |
|---|---|
| 做法 | `os.name == 'nt'` 时用 `powershell -NoProfile -NonInteractive -Command`，否则 `/bin/sh -c` |
| 别的方案 | 用 `shell=True` 走 cmd.exe |
| 为什么不用 | 模型见过的语料大多是 Unix 写法，`ls`、`cat`、`grep` 在 cmd 里都没有，会一路报"不是内部或外部命令"。PowerShell 自带这些别名，能少掉一批无谓失败 |
| 测出来的 | 真实任务里 `Get-ChildItem` 和 `ls` 都能跑；`test_runs_in_workspace` 守这条 |
| 实测的代价 | 让它数文件时，第一步写的 Unix 管道命令失败了（2 次工具调用里失败 1 次）。**但这恰好说明退出码有用**：它看到 exit=1 之后自己换了 PowerShell 写法 |
| 还没做的 | 混用 Unix 和 PowerShell 语法导致失败的比例没测。2 次调用样本太小，不能当失败率用 |
| 下一步 | 要么在系统提示里说明"这是 Windows，用 PowerShell 写法"，要么给 bash 工具的 schema 加一句说明。两种都要测过才知道哪个有效 |

## D7 文件工具的价值是场景相关的，不能笼统说"加了更好"

> ⚠️ **这条重测过三次，前两次的数据都作废了：**
> 第一次（n=2，只有可见测试判定）—— 判定器没跑隐藏测试（D24）；
> 第二次（n=4）—— 基准任务被实验自己污染（D26）。
> 下面是**第三次**：6 个任务、隐藏测试真正生效、工作区已移出仓库、每组 12–24 次运行。

**设置**：6 个任务 × 4 次 = 24 次/条件，`deepseek-flash`，`max_steps=12`，
系统提示词里带 shell 与解释器说明。

| 指标 | A 只有 bash | B 加文件工具 | 差 |
|---|---|---|---|
| **通过率** | **23/24（96%）** | **24/24（100%）** | +4 个点 |
| 平均步数 | 7.1 | 7.2 | 基本持平 |
| 平均输出 token | **1912** | **2336** | **+22%** |
| 工具调用失败率 | 10%（211 次里 22 次） | **7%**（230 次里 16 次） | 更低 |
| 想改测试被拦 | 0 | **2 次** | 权限层真的用上了 |

分任务看，方向和任务形状强相关：

| 任务 | A 通过 | B 通过 | A 步数/出token | B 步数/出token | 说明 |
|---|---|---|---|---|---|
| `t1_counter` 改一行 | 4/4 | 4/4 | 5.8 / 546 | 5.8 / 648 | 略贵 |
| `t2_ranges` 加分支 | 4/4 | 4/4 | 5.0 / 1549 | 6.2 / 1763 | 略贵 |
| `t3_median` 实现函数 | 4/4 | 4/4 | 7.5 / 2049 | **5.8 / 854** | **便宜 58%** |
| `t4_config` 改多行字典 | 4/4 | 4/4 | 8.0 / 1431 | **7.5 / 893** | **便宜 38%** |
| `t5_multi` 改两个文件 | 4/4 | 4/4 | 6.5 / 1494 | **6.0 / 1262** | 便宜 16% |
| `t6_spec` 按 SPEC 改语义 | **3/4** | **4/4** | 10.0 / 4404 | 12.0 / **8595** | **救回失败那跑，但贵 95%** |

| | |
|---|---|
| 怎么解释 | 改多行结构（`t3`/`t4`/`t5`）用 `edit_file` 明显便宜；改一行（`t1`/`t2`）反而多绕几步；`t6` 需要反复读 SPEC 和大文件，落盘再重读把它拖贵了 |
| 诚实的结论 | **文件工具不是单向改进**：通过率 96%→100%（就是救回 `t6` 那一跑），代价是整体多 22% token。但**工具失败率同时下降了**（10%→7%）—— 这一点和 n=2 时的观察相反 |
| 样本量 | 每组 24 次。比之前的 n=2 可信，但差异小（差 1 个案例），所以只能说"方向"，不能说"提升 4 个百分点" |
| 一个副产品 | 文件工具让 agent 更容易尝试去改测试（2 次被权限层拦下）—— 说明"防作弊第一道线"不是摆设 |

## D7b 更难的任务 + 正确的判定：通过率终于不是 100%

| | |
|---|---|
| 之前的困境 | 4 个任务两个条件全过，通过率这个维度什么都测不出来 |

## D8 超时必须杀掉整棵进程树

| | |
|---|---|
| 现象 | 评测卡在一个任务上十几分钟不动，背后有个 python 进程烧了 512 秒 CPU |
| 根因 | 原来用 `subprocess.run(timeout=...)`，超时只杀直接子进程（PowerShell）。PowerShell 拉起的 python 变成孤儿继续跑，而且握着 stdout 管道不放，`communicate()` 一直等 EOF —— 于是永远不返回 |
| 修法 | 改用 `Popen` + `communicate(timeout)`；超时后 Windows 走 `taskkill /F /T /PID`，POSIX 走 `killpg`，再补一次带超时的 `communicate` |
| 守住的测试 | `tests/test_tools.py::test_timeout_kills_and_returns_fast`：跑一个 sleep 30 的命令，1 秒超时，断言退出码 124 且总耗时不超 15 秒 |
| 能讲的点 | "超时"这件事最容易被做成假的：看起来设了超时，实际进程还在后台跑。这类 bug 不会报错，只会让整个评测偶发卡死 |

## D9 实验设计踩的坑：通过率撞天花板

| | |
|---|---|
| 第一版 | `max_steps=8`。8 次运行**全部**停在上限，`ok=False`，只是碰巧在预算耗尽前改完了文件 |
| 问题 | 数据作废。它测的不是"能不能做完"，而是"能不能在 8 步内做完" |
| 第二版 | `max_steps=12`，运行能自己收尾了（步数 5–12 分布） |
| 又一个问题 | 4 个任务两个条件**全部 100% 通过**。基线满分，消融在正确率这个维度上什么都证明不了 |
| 教训 | 任务集必须有难度梯度。满分基线等于没测 |
| 后续 | 要么加更难的复合任务（多文件、需要跨文件改），要么就承认当前结论只在"步数和花费"上成立 |

> 这条和上一个项目踩的是同一个坑：**指标撞天花板时，"没有差异"不等于"没有价值"，等于"这个测试测不出来"。**

## D10 防作弊两条线是互补的，单独一条都不够

| | |
|---|---|
| 权限层 | `write_file` / `edit_file` 改测试文件直接拒（`protected_file`）。实测真实运行里触发了 **3 次** |
| 哈希比对 | 跑完比对 `tests/` 下文件的哈希。实测抓住 **1 次** —— agent 用 bash 的 `Set-Content` 重写了 `tests/test_stats.py`，这条路权限层管不到 |
| 为什么两条都要 | 权限层管文件工具，管不到 shell；哈希比对能发现"改过了"，但拦不住。一个负责防，一个负责查 |
| 静态检查 | `sys.exit(0)`、裸 `except: pass` 也会标记，但这些检查很粗，只能当线索 |
| 诚实的边界 | 现在是"看得见改了测试"，还做不到"看出答案碰巧对了但逻辑是硬编码的" |

## D11 系统提示词里说明 shell 环境，shell 不匹配的失败从 6 次降到 0 次

| | |
|---|---|
| 做法 | `prompts.default_system()` 按 `os.name` 生成提示词：Windows 下加一段"底层是 PowerShell，别用 wc / tail / 2>/dev/null" |
| 别的方案 | ① 什么都不说，让模型自己试错 ② 只改工具描述不改系统提示词 ③ 让工具层去翻译 Unix 命令 |
| 为什么选这个 | 判断用 `os.name`，和 `tools/bash.py` 选 shell 用的是同一个判断 —— "实际用哪个 shell"和"告诉模型用哪个 shell"不会说两套话（`tests/test_prompts.py` 守住这条） |
| 实测设置 | 4 任务 × 2 次 = 8 次/组，`deepseek-flash`，`max_steps=12`，只有提示词一个变量 |

| | A 不给说明 | B 给出说明 |
|---|---|---|
| 通过 | 8/8 | 8/8 |
| 工具调用 | 67 | 62 |
| 非 0 退出 | 22（32.8%） | 18（29.0%） |
| └ 测试红（正常信号） | 10 | 4 |
| └ **shell 不匹配** | **6** | **0** |
| └ 其它（多为路径猜错） | 5 | 12 |
| 平均步数 | 8.38 | 8.25 |
| 平均出 token | 1358 | 1329 |

| | |
|---|---|
| 结论 | **这一类失败被完全消掉了**（6 → 0）。剩下非 0 的退出里，要么是测试没过的正常信号，要么是模型猜错文件路径，跟 shell 无关 |
| 没达到的预期 | 步数和 token 基本没变，通过率也没变（都满分）。所以这个改动的收益是"少浪费 6 次调用"，不是"变快了" |
| 样本量 | 每组 8 次。"6 → 0"这个差别方向明确，但要说"降低百分之多少"样本不够 |

## D12 我一开始的"工具失败率"口径是错的

| | |
|---|---|
| 错误做法 | 把 `exit_code != 0` 一律算成"工具调用失败" |
| 为什么错 | `pytest` 发现测试不通过时返回 1。那是 agent 需要的信息，不是工具坏了。混在一起算，"工具失败率 29%" 这个数字既没法解释，也没法拿来判断改动有没有用 |
| 发现方式 | 拆开看才发现：22 次非 0 里有 10 次是测试红 |
| 修法 | 加 `eval/failure_kinds.py`，按原因分成 `ok` / `test_red` / `shell_mismatch` / `other` 四类，逐条调用都记 `kind` |
| 修正后的真实数字 | 真正的环境性问题只有 **6 次（9%）**，不是我一开始说的 29% |
| 教训 | **指标定义错了，数字会看起来完全合理，然后一路错下去。** 先问"这个数在数什么"，再问"它是多少" |

## D13 事件流用 SSE，不用 WebSocket

| | |
|---|---|
| 做法 | `GET /runs/{id}/events` 返回 `text/event-stream`，事件按 `event: 类型 / data: JSON` 推 |
| 别的方案 | ① WebSocket ② 客户端轮询 `GET /runs/{id}` ③ 等跑完一次性返回 |
| 为什么不用 ③ | 一个任务几十秒，中间什么都看不到，等于没有服务层 |
| 为什么不用 ② | 能work，但要自己定轮询间隔：太密浪费，太疏丢细节。而且要额外维护"上次看到哪了" |
| 为什么不用 ① | 这里只需要服务端往客户端单向推。WebSocket 要引入握手、心跳、重连协议，用不上 |
| SSE 的额外好处 | **`curl` 就能验证**，不用写客户端。断线重连还能续推 —— 因为事件都留在 `RunState.events` 里，生成器按序号补发 |
| 实测 | `curl -sN` 拿到完整 6 条：`start` → `model_call` → `tool_call` → `model_call` → `finish` → `end`，真实任务 2 步答对 |
| 局限 | 客户端不能往回发消息。以后要做"运行中插话/打断"，得换成 WebSocket 或加一个 POST 接口 |

## D14 主循环跑在线程里，事件用 asyncio.Event 桥接

| | |
|---|---|
| 问题 | 主循环是同步阻塞的（`subprocess`），FastAPI 是异步的。两者要碰头 |
| 别的方案 | ① 把主循环改成 async ② SSE 生成器忙轮询 ③ 线程 + 事件通知 |
| 为什么不用 ① | 要动核心代码（`subprocess.run` 换 `asyncio.create_subprocess_exec`），而核心已经跑通了，为了服务层去改它不划算 |
| 为什么不用 ② | 忙轮询要定 sleep 间隔，间隔大丢实时性，间隔小空转 CPU |
| 采用 ③ 的做法 | run 在 `threading.Thread` 里跑；每产生一个事件，线程 `append` 到 `state.events`，再 `loop.call_soon_threadsafe(cs.set)` 唤醒 SSE 生成器；生成器记住发到第几条，醒来就补发 |
| 踩到的坑 | **服务退出时事件循环已经关了**，`call_soon_threadsafe` 会抛 `RuntimeError`。不接住的话后台线程会安静地死掉，run 永远停在 `running` |
| 兜底 | 生成器还有 15 秒 `keepalive` 注释帧，防止中间层把闲置连接掐掉 |
| 测的 | `tests/test_service.py` 7 个用例：生命周期、SSE 内容、404、422、被拒事件、provider 抛异常时状态转 `error` |

## D15 事件交给 store 管，按序号读

| | |
|---|---|
| 原来 | `app` 里直接往 `RunState.events` 这个 list 追加，SSE 生成器从 list 里读 |
| 问题 | 这套只在单进程内成立。换成 Redis 之后，事件必须能被另一个进程读到；而且**进程被杀掉再起来，内存里那个 list 就是空的**，"断线重连接着推"也就无从谈起 |
| 改法 | store 增加 `append_event` / `read_events(run_id, start)`；SSE 生成器只记一个 `sent` 序号，醒来就补发 `read_events(id, sent)`。内存版和 Redis 版实现同一个接口 |
| 好处 | 调用方不用关心底下是内存还是 Redis；断线重连天然支持，因为事件是有序的、可重放的 |
| 实测 | 杀掉 uvicorn 进程再起来：`GET /runs/{id}` 仍返回 `done` 和结果，`GET /runs/{id}/events` 能把重启前的 5 条事件重放出来 |

## D16 检查点必须在**工具结果补齐之后**存

| | |
|---|---|
| 做法 | `loop` 每轮把工具执行完、`tool_result` 追加进 `messages` 之后，才调 `on_step` 存检查点 |
| 如果存早了会怎样 | `messages` 里会有"assistant 说要调工具，但没有对应 tool_result"的状态。用这个状态发下一次请求，服务端会直接 400 —— 对话结构不合法 |
| 实测的检查点结构 | 3 条消息：`user`（任务）→ `assistant`（带 tool_use）→ `user`（tool_result）|
| 恢复时的接续 | `resume` 传入 `{"messages": [...], "step": n, "usage": {...}}`，主循环从 `n+1` 步继续，步数**接着数而不是从 1 重来**（实测 1 → 3 步完成） |

## D19 桩和真实不一致的检查是无效的

| | |
|---|---|
| 现象 | 用户在浏览器里提交任务，事件正常滚动，但**收尾那一行显示成一对空括号**，结果面板不出现，控制台报 `Cannot read properties of undefined (reading 'result')` |

| 教训 | **用桩做的检查，只能证明"假设的输入能被处理"。** 要证明端到端一致，必须拿真实输出当夹具，或者在契约层加断言（这里就是"统一的事件外壳"）。 |

## D23 上下文压缩：省 45% 输入 token，但阈值定错等于没开

| | |
|---|---|
| 三种手段 | ① 单个工具结果超阈值就**落盘**，上下文里只留头尾和路径<br>② 最近 N 个工具结果保留全文，更早的截断<br>③ 消息太多时**删掉最早的整对**（assistant + 它的 tool_result） |
| 最关键的不变式 | **绝不能把 tool_use 和它的 tool_result 拆开。** 拆了下一次请求直接 400，而且报错跟压缩毫无关系 |
| 这个坑真踩到了 | 第一版剪枝切点算成 `i+1`，只删 assistant 留着 tool_result —— 被"不许出现孤立 tool_result"的测试当场抓住，改成 `i+2` |
| 实测（A/B，n=2） | 输入 token **7419 → 6012（−19%）**；压缩触发 5 次，共省 23798 字符 |
| 但代价也很清楚 | **2 次里 1 次没完成**，步数 3.0 → 4.0，耗时 12.1 → 16.1 秒 |
| 怎么解释 | 工具输出被落盘之后，模型想再看得用 read_file 重读一遍，多花一步。省的是**每轮重发的 token**，付的是**偶尔多一步** |
| **n=3 复测（阈值调优）** | 见下表。**默认档反而最好** —— 上一轮那个"没完成"是小样本波动 |

| 档位（单次落盘阈值 / 保留 recent） | 完成数 | 平均输入 token | 压缩次数 |
|---|---|---|---|
| A 不压缩 | 2/3 | 7597 | 0 |
| **B 默认档 4000 / 3** | **3/3** | **4185（−45%）** | 7 |
| C 宽松档 12000 / 5 | 2/3 | 5800 | **0** |

| 意外发现 | **C 档一次都没触发压缩** —— 阈值 12000 比要读的文档（11396 字符）还大，等于没开。所以 C 组的结果其实是"不压缩 + 随机波动" |
| 教训 | **阈值必须相对语料大小来定。** 拍一个大数字上去等于关掉功能，而且从指标上看不出来（只会觉得"压缩没效果"） |
| 结论 | 默认 4000 保留。真要调，应该按语料分位数（比如 p80）来定，不是拍脑袋 |

## D31 多轮对话：起一个新 run，把上一轮的消息接上

| | |
|---|---|
| 用户反馈 | "每一次会话提交之后任务都会结束，不能进行下一轮对话" |
| 根因 | 之前的设计是**一次 run = 一句话**。run 结束（`finish`）后不保存检查点，所以完成之后没有任何可续的状态；`resume` 只服务于"被步数上限打断"的 run |
| 做法 | ① `loop.py` 正常收尾时也存一次检查点 —— 这样完成的 run 也有完整消息列表<br>② 新接口 `POST /runs/{id}/followup {text}`：取上一轮的 messages，**追加一条 user 消息**，然后起一个**新的 run**，`parent_id` 记成上一轮 |
| 为什么起新 run 而不是在原 run 上改 | 事件流、历史、检查点都是按 run 存的。起新 run 直接复用整套机制，只需把消息列表当起点；原 run 的记录也不会被改写（可回放） |
| 为什么要在 loop 里存最终检查点 | 不存就没有"这一轮结束时的完整对话"，followup 无从接起 |
| 一个必须区分的语义 | `done` 现在有两种：**正常收尾**（`result.ok=True`）和**步数耗尽被打断**（`ok=False`）。前者不该再 `resume`（会在没有新用户输入的情况下再调一次模型），后者才是 `resume` 的用途。所以 `resume` 里按 `result.ok` 分流，正常完成的提示"请用 followup" |
| 实测（真实模型，三轮） | ①"记住暗号：蓝鲸七号" → 记住了<br>②followup"暗号是什么" → **蓝鲸七号**<br>③再 followup"我上一条问了你什么" → **你上一条问我：刚才让你记住的暗号是什么** |
| 实测（复验） | "暗号：海豚三号" → 好的；followup 问"两个字" → **暗号是「海豚三号」——不过这是四个字，不是两个字**（说明上下文真的在） |
| 测试 | 5 条：上下文确实带上了（截获 provider 收到的 messages 断言长度和内容）、三轮链条、未知 run 404、空文本 400、无检查点 409 |
| 前端 | run 结束后提交按钮变成「接着说」并出现「新会话」按钮；「接着说」走 followup 并订阅新 run；「新会话」清空关联 |

## D32 桌面窗口白屏：查了四种假设，最后靠"验证 + 三级降级"收口

| | |
|---|---|
| 用户反馈 | "`.venv\Scripts\minicode.exe app` 返回服务已就绪，但弹出的窗口是空白的，左上角显示 `127.0.0.1_/`" |

| 顺便加的 | `--mode auto/app/window` 可以强制指定；`--dry-run` 打印两种模式的完整参数 |
| 没能验证的 | 在**不受限终端**里 `--app` 是否真的正常 —— 我这边所有子进程都受沙箱影响，无法给出确定结论。所以做成自动检测 + 降级，而不是断言某一种模式一定好 |

## D35 主循环加固：resume 空转、截断当成功

| | |
|---|---|
| 问题一 | resume 的 `max_steps` 被当成"绝对步数"：检查点正好停在 max_steps 时，续跑循环一次都不进，**直接返回 ok=False** —— 界面上点「继续跑」看到的是"没反应" |
| 修法一 | `max_steps` 改成"**再给几步**"：`end_step = start_step + max_steps - 1` |
| 问题二 | `stop_reason=max_tokens`（回答被截断）被当成 `ok=True`，半截答案会被算成功 |
| 修法二 | 只有模型自己收尾（非 max_tokens / refusal）才算成功 |
| 问题三 | provider 和工具都没有异常边界：一次网络异常或一个 GBK 文件就让整个 run 挂掉 |

| 修法四 | 最后一步只给"未执行"的结果，不真跑 |
| 问题五 | `tool_calls` 用"模型调用数 - 1"填充：并行 3 次调用记成 1、一次没调记成 -1 |

## D36 服务层加固：事件流与状态机

| | |
|---|---|
| SSE 每次重连从 0 重放 | 浏览器 EventSource 自动重连时会带 `Last-Event-ID`，但服务端既不发 `id:` 也不读它 → 整段事件重复发。修：每条事件发 `id: <序号>`，连接时读 `Last-Event-ID` 续发，并加 `retry: 3000` |

| 之前 | README 的"还差什么"里列着：只能等它自己结束 |

## D52 打开工作区返回 HTTP 500：os.startfile 不能在线程池里用

| | |
|---|---|
| 现象 | 点「打开工作区目录」，界面提示 `打开失败：HTTP 500` |
| 根因 | 接口是同步路由，FastAPI 把它放在**线程池线程**里执行；而 `os.startfile` 依赖的 COM 没有在该线程初始化 —— 实测直接抛 `PermissionError: [WinError 5] 拒绝访问`，未捕获就变成 500 |
| 修法 | 打开目录改用 `explorer.exe <path>` 子进程（不碰 COM，退出码即使是 1 也忽略）；命令抽成 `open_command(path, platform)` 便于单测 |
| 顺带 | 打开失败不再裸奔 500：捕获 OSError 后返回 `HTTPException(500, "打开目录失败：…")`，前端会把它显示出来（`api.ts` 本来就会取响应里的 detail） |
| 验证 | 真实调用 `POST /workspaces/open` 默认工作区 → **HTTP 200**，资源管理器真的弹出；越界目录仍 403；新增 2 条测试（三平台命令映射、失败时错误信息可读） |

## D53 打开工作区目录：HTTP 500 / explorer 崩溃弹窗的完整定位

| | |
|---|---|
| 现象 | 点「打开工作区目录」先是 HTTP 500，改成 explorer 子进程后弹 `explorer.exe - Application Error` |
| 排查路径 | ① 线程池 + COM 没初始化 → 加 `CoInitialize` 后仍 `WinError 5`<br>② 主线程直接 `os.startfile` 同样 500 → 排除线程<br>③ `ShellExecuteW` 返回 5（SE_ERR_ACCESSDENIED）→ 排除参数/路径<br>④ `cscript` 调 `Shell.Application` COM：在 pwsh 上下文**成功**，在服务上下文 200 但不弹窗<br>⑤ 用计划任务把服务搬到交互会话（父进程链 → svchost，脱离工具沙箱）**仍然失败** → 排除 DSH 进程树<br>⑥ 查 `%TEMP%` ACL：里面有一个陌生沙箱的用户组和一条未解析 SID |
| 结论 | 这台机器上装过别的沙箱工具（它的用户组出现在 %TEMP% 的 ACL 里），进程跑在**受限令牌**里；Windows 拒绝受限令牌进程发起 `ShellExecute`（`WinError 5`），直接 spawn `explorer.exe` 则会让它崩溃弹 Application Error。**这不是代码能绕过的** |
| 最终实现 | Windows：先 `os.startfile`（系统标准做法）→ 失败则 `cscript + Shell.Application COM` 兜底 → 都失败把两种原因一起返回 |
| 界面兜底 | 打开失败时前端把**工作区路径复制到剪贴板**并提示原因，用户可以直接粘到资源管理器地址栏 |
| 验证 | 单测覆盖三种情况（startfile 优先 / 回退 COM / 两种都失败时错误信息含两种原因）；正常桌面环境下 `os.startfile` 是标准路径，本次失败是环境限制 |

## D57 MCP 接入（Protocol 2026-07-28 现代版 + 2025-11-25 旧版回退）

| | |
|---|---|
| 协议决定 | 官方 spec 已到 **2026-07-28**：**没有 initialize 握手**，每个请求在 `_meta` 里带协议版本/客户端信息/能力，响应带 `resultType`。`≤2025-11-25` 仍是握手式。客户端**先按现代版发，被拒再按旧版 initialize 回退**（2025-11-25 → 2025-06-18 → 2024-11-05），这样新 server 和老 server 都能对接 |
| 传输 | 只做 **stdio**（JSON-RPC 2.0 按行）。不做 HTTP/SSE：那要开监听端口 + 鉴权面，和"只监听 127.0.0.1"的原则冲突 |
| 配置 | `<workspace>/.minicode/mcp.json`：`servers: [{name, command, args, env, cwd, enabled, allow, timeout}]`。**`enabled` 默认 false**，`allow` 是枚举白名单、默认拒绝未知工具 |
| 工具命名 | `mcp__<server>__<tool>`，和内置工具不冲突；界面上显示成 `server/tool` 并加 **MCP** 徽标 |
| 治理（三层） | ①配置层：没 `enabled` 不连；工具不在 `allow` **根本不注册**，模型看不到 ②适配层：`McpTool.run` 再查一次白名单（防绕过注册）③审计层：`tool_call` 事件的 `meta` 带 `source=mcp / server / mcp_tool / duration_ms / mode / protocol_version` |
| 为什么不走 policy | bash 能分词判命令、文件工具能判路径；MCP 工具参数语义对外部是不透明的，判不了。所以把"信任"显式化：允许哪个 server、哪个工具，写进配置，默认全拒 |
| 失败隔离 | 调用超时（默认 30s，可配）→ 工具错误；server 退出 → 工具返回错误并带 stderr 摘要，主循环继续；输出 20KB 截断 |
| 界面 | 输入区加「MCP」开关（**默认关**）；右栏工具行显示 `server/tool` + MCP 徽标；原始事件多一条 `mcp_ready`（几个 server、几个工具） |
| 真实数字 | `mcp check`：启动+握手 **105.6ms**；2 个允许工具的 schema **342 字符 ≈ 213 tokens/轮**（server 共 5 个工具，未允许的 3 个不占 token）；单次 `add` 调用 **0.2ms**。CLI 真跑（`--mcp`，用 add+echo 两个工具）：3 步 / 入 1130 出 227 token / 3.5s。服务端真跑：2 步 / 入 354 出 80 / 5.2s |
| 明确不做 | HTTP transport、resources/prompts/sampling、MRTR（server 要求补输入时直接报错）、多 server 并行、自动重启 |
| 安全提醒 | 配置里写 `command` 等于允许它在**本机执行任意代码**，这是 MCP 固有风险。所以默认 `enabled: false` + 白名单；`minicode mcp check` 会先把完整命令行打出来让你确认 |
| 测试 | 33 条：配置解析/默认关/坏配置；现代握手、旧版回退、纯现代 server；白名单注册层 + 运行时二次校验（`write_note` 被拒时**文件真的没被写**）；超时；崩溃隔离；结果渲染（图片/资源/截断）；提示词；主循环调用；服务层 mcp=true 真连、mcp=false 不连、followup 继承、Redis 字段往返 |
