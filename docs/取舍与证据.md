# 取舍与证据

每做一个决定记一条：**其他方案是什么、为什么不用、实际测出来多少**。

写这个是因为面试时会问"你为什么这么做"。到时候翻这里，别靠回忆。
反过来也一样：没有测过的，这里就写"还没测"。

## D1 工具返回值保留退出码

| | |
|---|---|
| 做法 | `ToolResult` 里带 `exit_code`，给模型看的内容前面加 `[exit=N]` |
| 别的方案 | 把 stdout 和 stderr 拼成一段文本返回（最常见） |
| 为什么不用 | 拼文本会把失败信息抹平。命令报错了，模型看到一大段输出，不知道它失败了，会接着往下瞎猜 |
| 测出来的 | `tests/test_tools.py::test_failure_keeps_exit_code` 守住这条；真实任务里 `tool_call` 事件记到 `exit_code=0`、`failed=false` |
| 一个真实例子 | 让它数 `src/minicode/tools` 下几个 py 文件。第一步它写了 `ls src/minicode/tools/*.py 2>/dev/null \| wc -l`，在 PowerShell 下 `wc` 不存在、`2>/dev/null` 也不合法，退出码 1。**因为看到了 exit=1，它第二步换成 `(Get-ChildItem ... -Filter *.py).Count`，然后答对 3** |
| 如果丢掉退出码会怎样 | 模型看到的是一段空输出，很可能直接答"0 个文件"。所以这个决定不是洁癖，它直接改变了行为 |
| 能讲的点 | 失败率能不能算，取决于退出码有没有留下来。这是个"看起来无所谓、实际决定能不能评测"的细节 |

## D2 权限用分词加参数判定，不用子串黑名单

| | |
|---|---|
| 做法 | 先把命令按 `;` `&&` `\|\|` `\|` 切成链，再 `shlex` 分词拿到程序名和参数，按参数语义判 |
| 别的方案 | `if "rm -rf" in cmd` 这类子串匹配 |
| 为什么不用 | 见下面的实测。子串匹配同时会漏和会误伤 |
| 测出来的 | 16 条危险 + 12 条正常：拦截率 **56.2% → 100%**，误报率 **33.3% → 0%**。结果在 `eval/runs/perm_*.json` |
| 漏掉的典型 | `rm  -rf   /`（多空格）、`rm -fr /`（参数顺序）、`git reset --hard`、`git clean -fdx`、`chmod -R 777 /`、`echo hi > /etc/passwd`、`:(){ :\|:& };:` |
| 误伤的典型 | `echo "rm -rf /"`、`grep -r "rm -rf" .`、`rm -rf ./build`、`echo 'shutdown'` |
| 还没做的 | 用例是我自己写的，不是从真实操作日志里抽的。这个对比能说明两种方法差很多，不能说明结构化判定在真实环境也是 100% |

## D3 Windows 上用 PowerShell 当 shell

| | |
|---|---|
| 做法 | `os.name == 'nt'` 时用 `powershell -NoProfile -NonInteractive -Command`，否则 `/bin/sh -c` |
| 别的方案 | 用 `shell=True` 走 cmd.exe |
| 为什么不用 | 模型见过的语料大多是 Unix 写法，`ls`、`cat`、`grep` 在 cmd 里都没有，会一路报"不是内部或外部命令"。PowerShell 自带这些别名，能少掉一批无谓失败 |
| 测出来的 | 真实任务里 `Get-ChildItem` 和 `ls` 都能跑；`test_runs_in_workspace` 守这条 |
| 实测的代价 | 让它数文件时，第一步写的 Unix 管道命令失败了（2 次工具调用里失败 1 次）。**但这恰好说明退出码有用**：它看到 exit=1 之后自己换了 PowerShell 写法 |
| 还没做的 | 混用 Unix 和 PowerShell 语法导致失败的比例没测。2 次调用样本太小，不能当失败率用 |
| 下一步 | 要么在系统提示里说明"这是 Windows，用 PowerShell 写法"，要么给 bash 工具的 schema 加一句说明。两种都要测过才知道哪个有效 |

| | |

## D5 指标从事件算，不解析日志

| | |
|---|---|
| 做法 | 每次模型调用、每次工具调用、每次拒绝都写一条结构化事件；轨迹存 `eval/runs/*.json` |

| 能讲的点 | 这就是"数字能被复核"的具体做法 |

## D7 文件工具的价值是场景相关的，不能笼统说"加了更好"

> ⚠️ **这一条的数据在 2026-11-13 晚重测过。** 第一版（4 个任务、只有可见测试判定）
> 的结论作废了 —— 见 D24：判定器当时根本没跑隐藏测试。
> 下面是**修正后**的数据：6 个任务（含 2 个加难度的）、隐藏测试真正生效、每组 12 次运行。

| | |
|---|---|
| 做法 | 加 `read_file` / `write_file` / `edit_file`，但 `build_registry()` 默认**不带**，要显式 `files=True` |
| 为什么这么做 | 要做消融实验，就得让"加不加工具"是一个可切换的变量 |

| 指标 | A 只有 bash | B 加文件工具 |
|---|---|---|
| **通过率** | **10/12（83%）** | **11/12（92%）** |
| 平均步数 | 7.5 | 7.8 |
| 平均输出 token | **1618** | **2433（多 50%）** |
| 工具调用失败率 | 9%（98 次里 9 次） | 18%（127 次里 23 次） |

分任务看，方向和任务形状强相关：

| 任务 | A 通过 | B 通过 | A 步数/出token | B 步数/出token | 说明 |
|---|---|---|---|---|---|
| `t1_counter` 改一行 | 2/2 | 2/2 | 5.5 / 518 | 6.0 / 634 | 略微变差 |
| `t2_ranges` 加分支 | 2/2 | 2/2 | 4.5 / 870 | 6.0 / 1682 | 变差 |
| `t3_median` 实现函数 | 2/2 | 2/2 | 5.5 / 1130 | 6.0 / 1032 | 持平 |
| `t4_config` 改多行字典 | 2/2 | 2/2 | 11.0 / 2228 | **6.0 / 848** | **明显更省** |
| `t5_multi` 改两个文件 | **1/2** | **1/2** | 10.0 / 2584 | 11.5 / 3256 | 两边都没稳定过 |
| `t6_spec` 按 SPEC 改语义 | **1/2** | **2/2** | 8.5 / 2380 | 11.0 / 7145 | **救回了失败那跑，但贵三倍** |

| | |
|---|---|
| 怎么解释 | `t4` 要改的是带中文和引号的多行字典，用 shell 重写整段容易转义出错，`edit_file` 只替换指定片段正好避开。`t1`/`t2` 只改一行，多给三个工具反而让模型多绕几步 |
| 诚实的结论 | **"加文件工具"不是一个单向的改进。** 它把通过率从 83% 抬到 92%，代价是多 50% 的 token 和翻倍的失败率。是否值得取决于任务：改多行结构代码值，改一行不值 |
| 样本量 | 每组 12 次。这个量级只能说方向，不能说"提升 9 个百分点" |

## D7b 更难的任务 + 正确的判定，终于让通过率不再是 100%

| | |
|---|---|
| 之前的困境 | 4 个任务两个条件全过，通过率这个维度什么都测不出来 |

## D8 超时必须杀掉整棵进程树

| | |
|---|---|
| 现象 | 评测卡在一个任务上十几分钟不动，背后有个 python 进程烧了 512 秒 CPU |
| 根因 | 原来用 `subprocess.run(timeout=...)`，超时只杀直接子进程（PowerShell）。PowerShell 拉起的 python 变成孤儿继续跑，而且握着 stdout 管道不放，`communicate()` 一直等 EOF —— 于是永远不返回 |
| 修法 | 改用 `Popen` + `communicate(timeout)`；超时后 Windows 走 `taskkill /F /T /PID`，POSIX 走 `killpg`，再补一次带超时的 `communicate` |
| 守住的测试 | `tests/test_tools.py::test_timeout_kills_and_returns_fast`：跑一个 sleep 30 的命令，1 秒超时，断言退出码 124 且总耗时不超 15 秒 |
| 能讲的点 | "超时"这件事最容易被做成假的：看起来设了超时，实际进程还在后台跑。这类 bug 不会报错，只会让整个评测偶发卡死 |

## D9 实验设计踩的坑：通过率撞天花板

| | |
|---|---|
| 第一版 | `max_steps=8`。8 次运行**全部**停在上限，`ok=False`，只是碰巧在预算耗尽前改完了文件 |
| 问题 | 数据作废。它测的不是"能不能做完"，而是"能不能在 8 步内做完" |
| 第二版 | `max_steps=12`，运行能自己收尾了（步数 5–12 分布） |
| 又一个问题 | 4 个任务两个条件**全部 100% 通过**。基线满分，消融在正确率这个维度上什么都证明不了 |
| 教训 | 任务集必须有难度梯度。满分基线等于没测 |
| 后续 | 要么加更难的复合任务（多文件、需要跨文件改），要么就承认当前结论只在"步数和花费"上成立 |

> 这条和上一个项目踩的是同一个坑：**指标撞天花板时，"没有差异"不等于"没有价值"，等于"这个测试测不出来"。**

## D10 防作弊两条线是互补的，单独一条都不够

| | |
|---|---|
| 权限层 | `write_file` / `edit_file` 改测试文件直接拒（`protected_file`）。实测真实运行里触发了 **3 次** |
| 哈希比对 | 跑完比对 `tests/` 下文件的哈希。实测抓住 **1 次** —— agent 用 bash 的 `Set-Content` 重写了 `tests/test_stats.py`，这条路权限层管不到 |
| 为什么两条都要 | 权限层管文件工具，管不到 shell；哈希比对能发现"改过了"，但拦不住。一个负责防，一个负责查 |
| 静态检查 | `sys.exit(0)`、裸 `except: pass` 也会标记，但这些检查很粗，只能当线索 |
| 诚实的边界 | 现在是"看得见改了测试"，还做不到"看出答案碰巧对了但逻辑是硬编码的" |

## D11 系统提示词里说明 shell 环境，shell 不匹配的失败从 6 次降到 0 次

| | |
|---|---|
| 做法 | `prompts.default_system()` 按 `os.name` 生成提示词：Windows 下加一段"底层是 PowerShell，别用 wc / tail / 2>/dev/null" |
| 别的方案 | ① 什么都不说，让模型自己试错 ② 只改工具描述不改系统提示词 ③ 让工具层去翻译 Unix 命令 |
| 为什么选这个 | 判断用 `os.name`，和 `tools/bash.py` 选 shell 用的是同一个判断 —— "实际用哪个 shell"和"告诉模型用哪个 shell"不会说两套话（`tests/test_prompts.py` 守住这条） |
| 实测设置 | 4 任务 × 2 次 = 8 次/组，`deepseek-flash`，`max_steps=12`，只有提示词一个变量 |

| | A 不给说明 | B 给出说明 |
|---|---|---|
| 通过 | 8/8 | 8/8 |
| 工具调用 | 67 | 62 |
| 非 0 退出 | 22（32.8%） | 18（29.0%） |
| └ 测试红（正常信号） | 10 | 4 |
| └ **shell 不匹配** | **6** | **0** |
| └ 其它（多为路径猜错） | 5 | 12 |
| 平均步数 | 8.38 | 8.25 |
| 平均出 token | 1358 | 1329 |

| | |
|---|---|
| 结论 | **这一类失败被完全消掉了**（6 → 0）。剩下非 0 的退出里，要么是测试没过的正常信号，要么是模型猜错文件路径，跟 shell 无关 |
| 没达到的预期 | 步数和 token 基本没变，通过率也没变（都满分）。所以这个改动的收益是"少浪费 6 次调用"，不是"变快了" |
| 样本量 | 每组 8 次。"6 → 0"这个差别方向明确，但要说"降低百分之多少"样本不够 |

## D12 我一开始的"工具失败率"口径是错的

| | |
|---|---|
| 错误做法 | 把 `exit_code != 0` 一律算成"工具调用失败" |
| 为什么错 | `pytest` 发现测试不通过时返回 1。那是 agent 需要的信息，不是工具坏了。混在一起算，"工具失败率 29%" 这个数字既没法解释，也没法拿来判断改动有没有用 |
| 发现方式 | 拆开看才发现：22 次非 0 里有 10 次是测试红 |
| 修法 | 加 `eval/failure_kinds.py`，按原因分成 `ok` / `test_red` / `shell_mismatch` / `other` 四类，逐条调用都记 `kind` |
| 修正后的真实数字 | 真正的环境性问题只有 **6 次（9%）**，不是我一开始说的 29% |
| 教训 | **指标定义错了，数字会看起来完全合理，然后一路错下去。** 先问"这个数在数什么"，再问"它是多少" |

## D13 事件流用 SSE，不用 WebSocket

| | |
|---|---|
| 做法 | `GET /runs/{id}/events` 返回 `text/event-stream`，事件按 `event: 类型 / data: JSON` 推 |
| 别的方案 | ① WebSocket ② 客户端轮询 `GET /runs/{id}` ③ 等跑完一次性返回 |
| 为什么不用 ③ | 一个任务几十秒，中间什么都看不到，等于没有服务层 |
| 为什么不用 ② | 能work，但要自己定轮询间隔：太密浪费，太疏丢细节。而且要额外维护"上次看到哪了" |
| 为什么不用 ① | 这里只需要服务端往客户端单向推。WebSocket 要引入握手、心跳、重连协议，用不上 |
| SSE 的额外好处 | **`curl` 就能验证**，不用写客户端。断线重连还能续推 —— 因为事件都留在 `RunState.events` 里，生成器按序号补发 |
| 实测 | `curl -sN` 拿到完整 6 条：`start` → `model_call` → `tool_call` → `model_call` → `finish` → `end`，真实任务 2 步答对 |
| 局限 | 客户端不能往回发消息。以后要做"运行中插话/打断"，得换成 WebSocket 或加一个 POST 接口 |

## D14 主循环跑在线程里，事件用 asyncio.Event 桥接

| | |
|---|---|
| 问题 | 主循环是同步阻塞的（`subprocess`），FastAPI 是异步的。两者要碰头 |
| 别的方案 | ① 把主循环改成 async ② SSE 生成器忙轮询 ③ 线程 + 事件通知 |
| 为什么不用 ① | 要动核心代码（`subprocess.run` 换 `asyncio.create_subprocess_exec`），而核心已经跑通了，为了服务层去改它不划算 |
| 为什么不用 ② | 忙轮询要定 sleep 间隔，间隔大丢实时性，间隔小空转 CPU |
| 采用 ③ 的做法 | run 在 `threading.Thread` 里跑；每产生一个事件，线程 `append` 到 `state.events`，再 `loop.call_soon_threadsafe(cs.set)` 唤醒 SSE 生成器；生成器记住发到第几条，醒来就补发 |
| 踩到的坑 | **服务退出时事件循环已经关了**，`call_soon_threadsafe` 会抛 `RuntimeError`。不接住的话后台线程会安静地死掉，run 永远停在 `running` |
| 兜底 | 生成器还有 15 秒 `keepalive` 注释帧，防止中间层把闲置连接掐掉 |
| 测的 | `tests/test_service.py` 7 个用例：生命周期、SSE 内容、404、422、被拒事件、provider 抛异常时状态转 `error` |

## D15 事件交给 store 管，按序号读

| | |
|---|---|
| 原来 | `app` 里直接往 `RunState.events` 这个 list 追加，SSE 生成器从 list 里读 |
| 问题 | 这套只在单进程内成立。换成 Redis 之后，事件必须能被另一个进程读到；而且**进程被杀掉再起来，内存里那个 list 就是空的**，"断线重连接着推"也就无从谈起 |
| 改法 | store 增加 `append_event` / `read_events(run_id, start)`；SSE 生成器只记一个 `sent` 序号，醒来就补发 `read_events(id, sent)`。内存版和 Redis 版实现同一个接口 |
| 好处 | 调用方不用关心底下是内存还是 Redis；断线重连天然支持，因为事件是有序的、可重放的 |
| 实测 | 杀掉 uvicorn 进程再起来：`GET /runs/{id}` 仍返回 `done` 和结果，`GET /runs/{id}/events` 能把重启前的 5 条事件重放出来 |

## D16 检查点必须在**工具结果补齐之后**存

| | |
|---|---|
| 做法 | `loop` 每轮把工具执行完、`tool_result` 追加进 `messages` 之后，才调 `on_step` 存检查点 |
| 如果存早了会怎样 | `messages` 里会有"assistant 说要调工具，但没有对应 tool_result"的状态。用这个状态发下一次请求，服务端会直接 400 —— 对话结构不合法 |
| 实测的检查点结构 | 3 条消息：`user`（任务）→ `assistant`（带 tool_use）→ `user`（tool_result）|
| 恢复时的接续 | `resume` 传入 `{"messages": [...], "step": n, "usage": {...}}`，主循环从 `n+1` 步继续，步数**接着数而不是从 1 重来**（实测 1 → 3 步完成） |

## D17 Redis 5 不认 RESP3，redis-py 8 默认却用 RESP3

| | |
|---|---|
| 现象 | 连接直接报 `ResponseError: unknown command 'HELLO', with args beginning with: '3'` |
| 原因 | RESP3 握手靠 `HELLO` 命令，这个命令是 Redis 6 才加的。本机装的是便携版 Redis **5.0.14.1**，没有它 |
| 修法 | `redis.Redis.from_url(..., protocol=2)` 显式用 RESP2 |
| 为什么值得记 | 报错信息是 `unknown command HELLO`，跟"连不上""被防火墙挡了"看起来完全不同。**如果只看到"服务端返回了错误"，很容易误判成版本或权限问题**，实际是客户端协议默认值和服务器版本对不上 |

## D18 前端不跑浏览器自动化，用"纯逻辑测试 + 接线检查 + DOM 链路检查"

| | |
|---|---|
| 想达到的目标 | 界面改坏了要能立刻发现，而不是打开浏览器点一遍 |
| 试过的方案 | ① jsdom 直接加载页面 ② Playwright + Chromium ③ 都不做，靠肉眼 |
| 为什么 ① 不行 | **jsdom 不支持 `<script type="module">`**。实测用 `JSDOM.fromURL(页面)` 加载后 `#store` 仍是页面默认值，因为打包的 ESM 根本没执行，**而且它不报错**。这个坑很危险：看起来"没报错"其实什么都没跑 |
| 为什么 ② 暂时没上 | 要下载整个 Chromium，而这台机器到外网要过不稳定的代理 |
| 实际采用的（三层） | ① **纯逻辑**抽到 `format.ts`，`node --test` 跑 11 条<br>② **接线**静态对账：`main.ts` 用到的 DOM id 和接口路径，跟 `index.html`、后端接口比，4 条<br>③ **DOM 链路**：`web/uicheck.mjs` 把构建产物手动 `eval` 进 jsdom，用桩 fetch / 桩 EventSource 走一遍"提交 → 收事件 → 渲染 → 显示结果"，6 条检查 |
| 第 ③ 层怎么绕开 module 限制 | bundle 里没有 import/export 语句（自包含），所以能当普通脚本 `window.eval` 执行。如果以后产物里出现 ESM 语法，这一层会失效，需要换方案 |
| 抓到过什么 | **结果面板被排在事件面板下面**，事件一滚就把结果挤出视野 —— 这是真实体验问题，纯逻辑测试和接线检查都发现不了。改成"结果 → 事件 → 历史"，并在结束时把结果滚进视野 |
| 顺手改掉的 | 原来每来一条事件就对那一行 `scrollIntoView`，会把用户手动往上翻的位置顶掉；改成容器 `scrollTop = scrollHeight` |
| jsdom 为什么没进 devDependencies | 只在这一处用得上，不想让 `npm ci` 变重。用法写在脚本开头：`npm install --no-save jsdom` |
| 仍然抓不到 | 真实浏览器里的 CSS 布局、字体、EventSource 的实际重连行为 |

## D19 桩和真实不一致的检查是无效的

| | |
|---|---|
| 现象 | 用户在浏览器里提交任务，事件正常滚动，但**收尾那一行显示成一对空括号**，结果面板不出现，控制台报 `Cannot read properties of undefined (reading 'result')` |
| 根因 | `end` 事件的 payload 形状和别的事件不一样：<br>普通事件 `{"kind":"model_call","ts":…,"data":{…}}`<br>end 事件 `{"status":"done","result":{…}}` —— **少了 kind/ts/data 那层包装**<br>前端把它当普通事件渲染 → 走默认分支画出一个空对象；再 `showAnswer(ev.data)` → `ev.data` 是 undefined → 抛异常 |
| 为什么测试没拦住 | ① 后端测试只断言"文本里有 `event: end`"，没查 payload 形状<br>② jsdom 检查里我**自己用桩造了一个"正确"形状的 end 事件** —— 桩和真实不一致，于是检查只能证明"前端能处理正确形状"，证明不了"服务端发的就是正确形状" |
| 修法 | 服务端统一形状；前端 `showAnswer` 再兜一次底（`payload ?? {}`），以后形状改了最多显示"没有结果"，不会整块崩 |
| 补的测试 | `test_all_sse_events_share_envelope`：解析整条事件流，断言每条 data 都有 `kind` / `ts` / `data` 且 `data` 是对象。**验证过它能抓旧写法**：把服务端临时改回旧形状，这条测试就 FAILED |
| 教训 | **用桩做的检查，只能证明"假设的输入能被处理"。** 要证明端到端一致，必须拿真实输出当夹具，或者在契约层加断言（这里就是"统一的事件外壳"）。 |
| 顺带修的 | 浏览器控制台那个 `favicon.ico` 404 —— 加一行 `<link rel="icon" href="data:,">` |

## D20 权限判定退化成"钩子之一"

| | |
|---|---|
| 原来 | 主循环里直接调 `judge_tool_call()`，权限是写死的一步 |
| 改法 | 主循环只认 `HookBus`：`pre_tool` 跑一遍钩子，`post_tool` 再跑一遍。权限变成注册上去的一个钩子（`policy_hook`） |
| 换来什么 | 审计、拦截、参数改写、耗时统计都能挂上来，主循环不用再改。`post_tool` 还能拿到工具结果做统计 |

| 实测 | 13 条测试：拦截短路、改写透传、critical 两种行为、审计记录、`post_tool` 能看到 exit_code、危险命令仍然被拦（`by="policy"`） |
| 注意点 | 判定只覆盖**已知工具**（bash 和文件工具）。随手编个工具名是判不到的 —— 这条写进测试注释了，免得以后误以为"全都判了" |

## D23 上下文压缩：省 19% 输入 token，但有代价

| | |
|---|---|
| 三种手段 | ① 单个工具结果超阈值就**落盘**，上下文里只留头尾和路径<br>② 最近 N 个工具结果保留全文，更早的截断<br>③ 消息太多时**删掉最早的整对**（assistant + 它的 tool_result） |
| 最关键的不变式 | **绝不能把 tool_use 和它的 tool_result 拆开。** 拆了下一次请求直接 400，而且报错跟压缩毫无关系 |
| 这个坑真踩到了 | 第一版剪枝切点算成 `i+1`，只删 assistant 留着 tool_result —— 被"不许出现孤立 tool_result"的测试当场抓住，改成 `i+2` |
| 实测（A/B，n=2） | 输入 token **7419 → 6012（−19%）**；压缩触发 5 次，共省 23798 字符 |
| 但代价也很清楚 | **2 次里 1 次没完成**，步数 3.0 → 4.0，耗时 12.1 → 16.1 秒 |
| 怎么解释 | 工具输出被落盘之后，模型想再看得用 read_file 重读一遍，多花一步。省的是**每轮重发的 token**，付的是**偶尔多一步** |
| 诚实的结论 | 方向对，但阈值需要调。当前默认（单次 4000 字符就落盘）偏激进，n=2 也不足以定论 |
| 后续 | 调大阈值或提高"保留最近 N 个"再测；或者给落盘文件加一个"直接读回指定行范围"的便捷工具 |

## D25 沙箱提示词漏了"用哪个解释器"，agent 去 pip install 卡满超时

| | |
|---|---|
| 现象 | 沙箱任务单次耗时从 ~15 秒涨到 **73–87 秒**，失败分类里多了大量 `other` |
| 查轨迹 | 第 11 步是 `python -m pip ...`，`exit=124`（**超时**）。前面几步是 `python -m pytest` 失败、`py -m pytest` 也失败 |
| 根因 | 沙箱工作区里默认的 `python` 没装 pytest。agent 于是想 `pip install pytest`，而这台机器 PyPI 不通，命令挂到 60 秒超时被杀 |
| 更根本的原因 | **我在 CLI 里加了"该用哪个解释器"的提示，却忘了加在沙箱的系统提示词里。** 同一条信息，两个入口只有一个说了 |
| 修法 | `sandbox_run` 的系统提示词也传 `python_hint=sys.executable` |
| 教训 | 这类"两个入口说法不一致"的问题不会报错，只会让指标慢慢变脏：耗时翻五倍、失败率虚高。**凡是拼提示词的地方，都该共用同一个函数** |
| 顺带 | 这也说明超时处理很关键 —— 如果没有 `taskkill /F /T`（见 D8），这一步会挂到天荒地老 |
