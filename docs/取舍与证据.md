# 取舍与证据

每做一个决定记一条：**其他方案是什么、为什么不用、实际测出来多少**。

写这个是因为面试时会问"你为什么这么做"。到时候翻这里，别靠回忆。
反过来也一样：没有测过的，这里就写"还没测"。

---

## D1 工具返回值保留退出码

| | |
|---|---|
| 做法 | `ToolResult` 里带 `exit_code`，给模型看的内容前面加 `[exit=N]` |
| 别的方案 | 把 stdout 和 stderr 拼成一段文本返回（最常见） |
| 为什么不用 | 拼文本会把失败信息抹平。命令报错了，模型看到一大段输出，不知道它失败了，会接着往下瞎猜 |
| 测出来的 | `tests/test_tools.py::test_failure_keeps_exit_code` 守住这条；真实任务里 `tool_call` 事件记到 `exit_code=0`、`failed=false` |
| 一个真实例子 | 让它数 `src/minicode/tools` 下几个 py 文件。第一步它写了 `ls src/minicode/tools/*.py 2>/dev/null \| wc -l`，在 PowerShell 下 `wc` 不存在、`2>/dev/null` 也不合法，退出码 1。**因为看到了 exit=1，它第二步换成 `(Get-ChildItem ... -Filter *.py).Count`，然后答对 3** |
| 如果丢掉退出码会怎样 | 模型看到的是一段空输出，很可能直接答"0 个文件"。所以这个决定不是洁癖，它直接改变了行为 |
| 能讲的点 | 失败率能不能算，取决于退出码有没有留下来。这是个"看起来无所谓、实际决定能不能评测"的细节 |

## D2 权限用分词加参数判定，不用子串黑名单

| | |
|---|---|
| 做法 | 先把命令按 `;` `&&` `\|\|` `\|` 切成链，再 `shlex` 分词拿到程序名和参数，按参数语义判 |
| 别的方案 | `if "rm -rf" in cmd` 这类子串匹配 |
| 为什么不用 | 见下面的实测。子串匹配同时会漏和会误伤 |
| 测出来的 | 16 条危险 + 12 条正常：拦截率 **56.2% → 100%**，误报率 **33.3% → 0%**。结果在 `eval/runs/perm_*.json` |
| 漏掉的典型 | `rm  -rf   /`（多空格）、`rm -fr /`（参数顺序）、`git reset --hard`、`git clean -fdx`、`chmod -R 777 /`、`echo hi > /etc/passwd`、`:(){ :\|:& };:` |
| 误伤的典型 | `echo "rm -rf /"`、`grep -r "rm -rf" .`、`rm -rf ./build`、`echo 'shutdown'` |
| 还没做的 | 用例是我自己写的，不是从真实操作日志里抽的。这个对比能说明两种方法差很多，不能说明结构化判定在真实环境也是 100% |

## D3 Windows 上用 PowerShell 当 shell

| | |
|---|---|
| 做法 | `os.name == 'nt'` 时用 `powershell -NoProfile -NonInteractive -Command`，否则 `/bin/sh -c` |
| 别的方案 | 用 `shell=True` 走 cmd.exe |
| 为什么不用 | 模型见过的语料大多是 Unix 写法，`ls`、`cat`、`grep` 在 cmd 里都没有，会一路报"不是内部或外部命令"。PowerShell 自带这些别名，能少掉一批无谓失败 |
| 测出来的 | 真实任务里 `Get-ChildItem` 和 `ls` 都能跑；`test_runs_in_workspace` 守这条 |
| 实测的代价 | 让它数文件时，第一步写的 Unix 管道命令失败了（2 次工具调用里失败 1 次）。**但这恰好说明退出码有用**：它看到 exit=1 之后自己换了 PowerShell 写法 |
| 还没做的 | 混用 Unix 和 PowerShell 语法导致失败的比例没测。2 次调用样本太小，不能当失败率用 |
| 下一步 | 要么在系统提示里说明"这是 Windows，用 PowerShell 写法"，要么给 bash 工具的 schema 加一句说明。两种都要测过才知道哪个有效 |

## D4 主循环和 provider 解耦

| | |
|---|---|
| 做法 | `Provider` 协议只有一个 `complete()`，主循环只认 `ModelReply` |
| 别的方案 | 主循环里直接调 `anthropic` 客户端 |
| 为什么不用 | 那样主循环就没法离线测。现在用 `FakeProvider` 塞几条预设回复，就能确定地测：工具执行了没有、被拒之后模型收到什么、步数上限生效没有 |
| 测出来的 | `tests/test_loop.py` 4 个用例，不联网不花钱，跑完 0.1 秒 |
| 能讲的点 | 可测性是设计出来的，不是事后补的 |

## D5 指标从事件算，不解析日志

| | |
|---|---|
| 做法 | 每次模型调用、每次工具调用、每次拒绝都写一条结构化事件；轨迹存 `eval/runs/*.json` |
| 别的方案 | 打印日志，需要指标时用正则从日志里抠 |
| 为什么不用 | 日志是给人看的，格式一改指标就崩，而且崩了不报错 —— 只会算出一个错的数 |
| 测出来的 | 那个真实任务的轨迹：2 步、1 次工具调用、585 入 138 出 token、2.3 秒，全从事件读 |
| 能讲的点 | 这就是"数字能被复核"的具体做法 |

## D6 没有拿真实环境去试破坏性命令

| | |
|---|---|
| 做法 | 拒绝路径只在单测里验证（`test_denied_command_is_not_executed`），真机只跑正常任务 |
| 别的方案 | 让模型真去执行 `rm -rf /`，看拦不拦 |
| 为什么不 | 万一规则有洞，代价不可逆。为了多一个演示画面去赌整台机器不划算 |
| 换来什么 | 单测里能确定地断言"被拒的命令没有产生 `tool_call` 事件"，也就是真的没执行 |
| 诚实的说法 | 这条现在只有单元测试支撑，没有真实环境下的端到端验证 |

## D7 文件工具的价值是场景相关的，不能笼统说"加了更好"

| | |
|---|---|
| 做法 | 加 `read_file` / `write_file` / `edit_file`，但 `default_registry()` 默认**不带**，要显式 `include_files=True` |
| 别的方案 | 直接全给；或者只给 bash 不给文件工具 |
| 为什么这么做 | 要做消融实验，就得让"加不加工具"是一个可切换的变量 |
| 实测设置 | 4 个任务 × 2 次重复 = 8 次/条件，`deepseek-flash`，`max_steps=12` |
| 实测结果（通过率） | **两边都是 8/8，没有区分度** |
| 实测结果（花费） | 见下表，**方向和任务有关** |

| 任务 | 只有 bash 步数 / 出 token | 加文件工具 | 差 |
|---|---|---|---|
| `t1_counter`（改一行） | 6.0 / 742 | **10.0 / 1630** | 更差 |
| `t2_ranges`（加个分支） | 7.0 / 1346 | **9.5 / 1990** | 更差 |
| `t3_median`（实现一个函数） | 8.5 / 1338 | 7.5 / 984 | 略好 |
| `t4_config`（改多行字典，带中文和引号） | **11.0 / 1918** | 7.5 / 972 | **明显更省** |
| 平均 | 8.1 / 1336 | 8.6 / 1394 | 基本持平 |

| | |
|---|---|
| 怎么解释 | `t4` 要改的是一段多行字典，里面有中文和引号，用 shell 重写整段很容易转义出错；`edit_file` 只替换指定片段，正好避开这个。反过来 `t1` 只要改一行，多给三个工具反而让模型多绕几步（先 read 再 edit 再 read 确认） |
| 诚实的结论 | **我原本以为加了文件工具会全面提升，实测不是。** 工具的价值取决于任务形状，平均下来甚至略差 |
| 样本量 | 每格 2 次。这个量级只能看方向，不能说"提升了百分之多少" |

## D8 超时必须杀掉整棵进程树

| | |
|---|---|
| 现象 | 评测卡在一个任务上十几分钟不动，背后有个 python 进程烧了 512 秒 CPU |
| 根因 | 原来用 `subprocess.run(timeout=...)`，超时只杀直接子进程（PowerShell）。PowerShell 拉起的 python 变成孤儿继续跑，而且握着 stdout 管道不放，`communicate()` 一直等 EOF —— 于是永远不返回 |
| 修法 | 改用 `Popen` + `communicate(timeout)`；超时后 Windows 走 `taskkill /F /T /PID`，POSIX 走 `killpg`，再补一次带超时的 `communicate` |
| 守住的测试 | `tests/test_tools.py::test_timeout_kills_and_returns_fast`：跑一个 sleep 30 的命令，1 秒超时，断言退出码 124 且总耗时不超 15 秒 |
| 能讲的点 | "超时"这件事最容易被做成假的：看起来设了超时，实际进程还在后台跑。这类 bug 不会报错，只会让整个评测偶发卡死 |

## D9 实验设计踩的坑：通过率撞天花板

| | |
|---|---|
| 第一版 | `max_steps=8`。8 次运行**全部**停在上限，`ok=False`，只是碰巧在预算耗尽前改完了文件 |
| 问题 | 数据作废。它测的不是"能不能做完"，而是"能不能在 8 步内做完" |
| 第二版 | `max_steps=12`，运行能自己收尾了（步数 5–12 分布） |
| 又一个问题 | 4 个任务两个条件**全部 100% 通过**。基线满分，消融在正确率这个维度上什么都证明不了 |
| 教训 | 任务集必须有难度梯度。满分基线等于没测 |
| 后续 | 要么加更难的复合任务（多文件、需要跨文件改），要么就承认当前结论只在"步数和花费"上成立 |

> 这条和上一个项目踩的是同一个坑：**指标撞天花板时，"没有差异"不等于"没有价值"，等于"这个测试测不出来"。**

## D10 防作弊两条线是互补的，单独一条都不够

| | |
|---|---|
| 权限层 | `write_file` / `edit_file` 改测试文件直接拒（`protected_file`）。实测真实运行里触发了 **3 次** |
| 哈希比对 | 跑完比对 `tests/` 下文件的哈希。实测抓住 **1 次** —— agent 用 bash 的 `Set-Content` 重写了 `tests/test_stats.py`，这条路权限层管不到 |
| 为什么两条都要 | 权限层管文件工具，管不到 shell；哈希比对能发现"改过了"，但拦不住。一个负责防，一个负责查 |
| 静态检查 | `sys.exit(0)`、裸 `except: pass` 也会标记，但这些检查很粗，只能当线索 |
| 诚实的边界 | 现在是"看得见改了测试"，还做不到"看出答案碰巧对了但逻辑是硬编码的" |

## D11 系统提示词里说明 shell 环境，shell 不匹配的失败从 6 次降到 0 次

| | |
|---|---|
| 做法 | `prompts.default_system()` 按 `os.name` 生成提示词：Windows 下加一段"底层是 PowerShell，别用 wc / tail / 2>/dev/null" |
| 别的方案 | ① 什么都不说，让模型自己试错 ② 只改工具描述不改系统提示词 ③ 让工具层去翻译 Unix 命令 |
| 为什么选这个 | 判断用 `os.name`，和 `tools/bash.py` 选 shell 用的是同一个判断 —— "实际用哪个 shell"和"告诉模型用哪个 shell"不会说两套话（`tests/test_prompts.py` 守住这条） |
| 实测设置 | 4 任务 × 2 次 = 8 次/组，`deepseek-flash`，`max_steps=12`，只有提示词一个变量 |

| | A 不给说明 | B 给出说明 |
|---|---|---|
| 通过 | 8/8 | 8/8 |
| 工具调用 | 67 | 62 |
| 非 0 退出 | 22（32.8%） | 18（29.0%） |
| └ 测试红（正常信号） | 10 | 4 |
| └ **shell 不匹配** | **6** | **0** |
| └ 其它（多为路径猜错） | 5 | 12 |
| 平均步数 | 8.38 | 8.25 |
| 平均出 token | 1358 | 1329 |

| | |
|---|---|
| 结论 | **这一类失败被完全消掉了**（6 → 0）。剩下非 0 的退出里，要么是测试没过的正常信号，要么是模型猜错文件路径，跟 shell 无关 |
| 没达到的预期 | 步数和 token 基本没变，通过率也没变（都满分）。所以这个改动的收益是"少浪费 6 次调用"，不是"变快了" |
| 样本量 | 每组 8 次。"6 → 0"这个差别方向明确，但要说"降低百分之多少"样本不够 |

## D12 我一开始的"工具失败率"口径是错的

| | |
|---|---|
| 错误做法 | 把 `exit_code != 0` 一律算成"工具调用失败" |
| 为什么错 | `pytest` 发现测试不通过时返回 1。那是 agent 需要的信息，不是工具坏了。混在一起算，"工具失败率 29%" 这个数字既没法解释，也没法拿来判断改动有没有用 |
| 发现方式 | 拆开看才发现：22 次非 0 里有 10 次是测试红 |
| 修法 | 加 `eval/failure_kinds.py`，按原因分成 `ok` / `test_red` / `shell_mismatch` / `other` 四类，逐条调用都记 `kind` |
| 修正后的真实数字 | 真正的环境性问题只有 **6 次（9%）**，不是我一开始说的 29% |
| 教训 | **指标定义错了，数字会看起来完全合理，然后一路错下去。** 先问"这个数在数什么"，再问"它是多少" |

## D13 事件流用 SSE，不用 WebSocket

| | |
|---|---|
| 做法 | `GET /runs/{id}/events` 返回 `text/event-stream`，事件按 `event: 类型 / data: JSON` 推 |
| 别的方案 | ① WebSocket ② 客户端轮询 `GET /runs/{id}` ③ 等跑完一次性返回 |
| 为什么不用 ③ | 一个任务几十秒，中间什么都看不到，等于没有服务层 |
| 为什么不用 ② | 能work，但要自己定轮询间隔：太密浪费，太疏丢细节。而且要额外维护"上次看到哪了" |
| 为什么不用 ① | 这里只需要服务端往客户端单向推。WebSocket 要引入握手、心跳、重连协议，用不上 |
| SSE 的额外好处 | **`curl` 就能验证**，不用写客户端。断线重连还能续推 —— 因为事件都留在 `RunState.events` 里，生成器按序号补发 |
| 实测 | `curl -sN` 拿到完整 6 条：`start` → `model_call` → `tool_call` → `model_call` → `finish` → `end`，真实任务 2 步答对 |
| 局限 | 客户端不能往回发消息。以后要做"运行中插话/打断"，得换成 WebSocket 或加一个 POST 接口 |

## D14 主循环跑在线程里，事件用 asyncio.Event 桥接

| | |
|---|---|
| 问题 | 主循环是同步阻塞的（`subprocess`），FastAPI 是异步的。两者要碰头 |
| 别的方案 | ① 把主循环改成 async ② SSE 生成器忙轮询 ③ 线程 + 事件通知 |
| 为什么不用 ① | 要动核心代码（`subprocess.run` 换 `asyncio.create_subprocess_exec`），而核心已经跑通了，为了服务层去改它不划算 |
| 为什么不用 ② | 忙轮询要定 sleep 间隔，间隔大丢实时性，间隔小空转 CPU |
| 采用 ③ 的做法 | run 在 `threading.Thread` 里跑；每产生一个事件，线程 `append` 到 `state.events`，再 `loop.call_soon_threadsafe(cs.set)` 唤醒 SSE 生成器；生成器记住发到第几条，醒来就补发 |
| 踩到的坑 | **服务退出时事件循环已经关了**，`call_soon_threadsafe` 会抛 `RuntimeError`。不接住的话后台线程会安静地死掉，run 永远停在 `running` |
| 兜底 | 生成器还有 15 秒 `keepalive` 注释帧，防止中间层把闲置连接掐掉 |
| 测的 | `tests/test_service.py` 7 个用例：生命周期、SSE 内容、404、422、被拒事件、provider 抛异常时状态转 `error` |
