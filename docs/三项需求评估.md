## 一、task_system 比 todo_write 更严谨吗

**结论：严谨性你说得对，但它们解决的不是同一个问题。我建议"两条都留，用开关分开"，而不是替换。**

### 1.1 我读了 s10 的实现，它确实严谨在这几处

| 机制 | s10 的做法 | 我的 todo_write |
|---|---|---|
| **任务标识** | `task_` + 8 位随机十六进制，`"x"` 独占创建，冲突就重试（上限 100 次）| **没有 ID**，只有下标 |
| **依赖** | `blockedBy` 列表，加依赖时做 **DFS 环检测** | **没有依赖概念** |
| **可开工判定** | `can_start()`：前置没完成就不许开工；**前置文件读不到也算阻塞**（保守） | 无 |
| **认领与归属** | `claim_task(owner)`：只有 pending 且依赖满足才能认领，记下 owner | 只有一条 `in_progress`，没有 owner |
| **完成语义** | `complete_task()`：完成时**算出因为这一步而解锁了哪些任务**（完成前后各快照一次取差集） | 只改状态 |
| **持久化** | 每条任务一个 JSON 文件，跨进程可见 | **只在内存里，run 结束就没了** |

这几条里我认为最有价值的是两个：

- **环检测**：任务图出错的方式不是"报错"，而是"永远开不了工"，而且很难查
- **解锁报告**：完成一步之后主动告诉你"现在可以做 X 了"，这是把图结构变成可执行建议

### 1.2 但它多花了什么

**工具数量**。s10 是 6 个工具：`create_task` / `update_task` / `list_tasks` / `get_task` /
`claim_task` / `complete_task`。我们现在 6 个工具的定义已经占 **1532 字符 ≈ 510 token/轮**
（实测：bash 74、read_file 64、write_file 69、edit_file 97、todo_write 135、load_skill 69）。

再加 6 个 task 工具，按每个约 400 字符估：

```
单轮 +800 token 左右
一个 9 步任务，光是工具定义就要多发 ≈ 7200 token
```

对照一下：我们实测一个压缩后的任务**总输入 token 是 4185**。也就是说这 6 个工具的定义，
比整个任务的内容还贵。**在单代理场景下，这笔钱买不到对应的收益。**

### 1.3 更关键的区别：它们服务对象不同

| | todo_write | task_system |
|---|---|---|
| 回答的问题 | "我现在打算按什么顺序做" | "有哪些活、先后关系如何、谁在做" |
| 生命周期 | 一次 run | 跨 run、跨代理 |
| 典型使用者 | 单个 agent 自己 | 多代理 / 人或 agent 混合 |
| 更新方式 | **整份替换**（模型每次重写计划，很自然） | 增量操作（建/改/认领/完成） |

**证据**：参考项目里 s10 之后紧接着就是 s13 的 agent teams —— `task_system` 的
claim/owner 正是为"多个代理抢活"设计的。我们现在**只有一个子代理、而且它跑完就返回、
不共享任务板**，所以 claim/owner 现在没有消费者。

另外有一条实测值得提：我让模型用 `--plan` 跑过一次真实任务，**它一次都没调用
`todo_write`**（轨迹里 7 次工具调用全是 bash）。工具再多 6 个，被忽略的概率只会更高。

### 1.4 我的建议（按性价比排）

**方案 A（推荐）：把严谨性"选择性搬"进 todo，不搬工具数量**

给 `todo_write` 加两个字段，仍然是 1 个工具、仍然是整份替换：

```
todos: [{content, status, blockedBy: [下标或简写标签]}]
```

- 加**环检测**（提交时校验，有环就拒绝）
- 加**can_start 检查**：`in_progress` 的条目如果有未完成的 blockedBy，直接拒绝
- 保持整份替换语义 —— 模型重写计划比增量操作更不容易出错
- 成本：schema 从 407 涨到约 550 字符（+50 token/轮），可接受

**方案 B：要完整 s10 能力，就做成开关**

和 `--files` 一样的做法：`--tasks` 才挂那 6 个工具，默认不挂。这样：
- 想做"任务看板"或多代理时再开
- 消融实验里"加不加任务系统"仍然是一个干净变量

**方案 C（不推荐）：直接替换 todo_write**

理由是上面三条：工具贵、没有消费者、模型本来就不怎么用。

## 二、前端做得更全面

**结论：值得做，而且大部分不用改后端 —— 数据已经在事件流里了。**

### 2.1 先看现在缺什么

现在的界面只有三块：提交框、事件流、最终结果 + 历史列表。缺的按价值排：

| # | 缺的功能 | 数据从哪来 | 要不要改后端 |
|---|---|---|---|
| 1 | **计划面板**（当前 todo 状态） | `tool_call` 事件里 `args.todos` 就是完整清单 | **不用** |
| 2 | **花费汇总**（步数 / 入出 token / 耗时） | `model_call` 事件的 usage 累加 | **不用** |
| 3 | **中断的 run 加"继续跑"按钮** | `POST /runs/{id}/resume` 已存在 | **不用** |
| 4 | **失败与被拒的高亮/筛选** | `tool_call.failed`、`denied` 事件 | **不用** |
| 5 | 模型 / 最大步数 选择 | `POST /runs` 已支持这两个字段 | **不用** |
| 6 | 压缩触发的可视化 | `compact` 事件 | **不用** |
| 7 | 两次 run 并排对比 | 需要拉多次事件 | 不用（前端拼） |
| 8 | 任务看板（依赖图） | 需要先有 task_system | **要改后端** |

**关键点**：1–7 全部是纯前端工作。这也说明当初"事件流"这个设计选对了 ——
现在要加展示面，**后端一行都不用动**。

### 2.2 我的建议顺序

1. 先做 **1 + 2 + 3**（计划面板、花费汇总、续跑按钮）—— 这三个让界面从"能看"变成"能用"
2. 再做 **4 + 5 + 6**（筛选、参数选择、压缩可视化）
3. **8 留到 task_system 落地之后**

### 2.3 一个必须配的验证手段

现在前端测的是"纯逻辑 + 接线 + DOM 链路"（15 条 + uicheck 6 条检查）。
加面板之后要同步补：

- 每个新面板加一条纯逻辑测试（比如"从事件流里重建计划"这个函数）
- `uicheck.mjs` 里加对应断言
- 接线检查会自动覆盖新加的 DOM id（如果用了同一个 `el()` 函数）

## 三、桌面端入口

**结论：建议做"薄壳"，不要重写成桌面应用。先做最省的那个。**

### 3.1 一个前提判断：不要改成纯桌面端

现在这个项目的**卖点之一是它可被检查**：HTTP + SSE + `curl` 能看事件流，
面试官可以自己跑一遍。改成纯桌面应用会把这个优点收窄成"只能看截图"。

所以桌面端应当是 **同一个后端的另一个外壳**，而不是另起一套。

### 3.2 三种做法（都是实测过的环境事实）

| 方案 | 新增依赖 | 本机可行性 | 工时 | 观感 |
|---|---|---|---|---|
| **A. `msedge --app=URL`** | **0** | ✅ Edge 在 `C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe` | **~30 分钟** | 独立窗口、无地址栏，但本质是浏览器 |
| **B. pywebview** | `pywebview 6.2.1`（pip 有） | ✅ WebView2 运行时已装（157.0.4341.46） | 2–4 小时 | 真窗口，可 PyInstaller 打成 exe |
| **C. Electron** | electron（npm，约 100MB） | ⚠️ 代理不稳，下载有风险 | 4–6 小时 | 最"正规"，但最重 |
| D. Tauri | **需要 Rust** | ❌ `cargo` 没装 | — | — |
| E. PWA | 0 | ✅ | ~30 分钟 | 只是"添加到桌面"，没有窗口控制 |

### 3.3 我的建议

**先做 A，再决定要不要 B。**

A 的做法大概是：新增 `minicode app` 子命令 → 起 uvicorn（后台线程）→
`subprocess.Popen([msedge, "--app=http://127.0.0.1:8765", "--window-size=1100,800"])` →
关窗口时收掉服务。**三十行以内，零新依赖，而且 uvicorn 还在，`curl` 照样能用。**

B 的价值在于"能打包成 exe 发给别人"。但那要处理 PyInstaller + 静态资源 + WebView2 依赖，
属于"发布"问题，不是"能力"问题。**如果目标是面试演示，A 够了。**

### 3.4 一个风险要提前说

如果做 Electron/pywebview 打包，会遇到：静态资源路径、Python 依赖打包、首次启动速度。
这三件事都跟"agent 能力"无关，但会吃掉大量时间。**我建议等前端做完再考虑打包。**
