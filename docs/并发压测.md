# 并发与多会话压测

这份记录回答一个具体问题：**minicode 服务层同时跑很多 run / 很多会话时，会不会串会话、丢事件、丢 run？**

测的是服务层（worker 线程、store、SSE、会话分组、followup），不是模型质量。
所以用**假 provider**：不联网、不依赖 API key、不花钱，结果可复现。

## 怎么测

### 1. 回归测试（进 CI）

`tests/test_concurrency.py`，5 条：

| 测试 | 验证什么 |
|---|---|
| `test_concurrent_runs_are_isolated_and_grouped` | 20 个 run 同时建、同时跑：ID 唯一、事件不串任务、会话 20 条且各自 1 个 run |
| `test_concurrent_sse_streams_only_get_own_events` | 8 条 SSE 流并发读：每条都有 start/end，且只包含自己的事件 |
| `test_cancel_under_load_does_not_break_other_runs` | 10 个 run 同时跑，取消前 5 个：取消生效、其余正常完成、没有 error |
| `test_concurrent_followups_keep_conversations_separate` | 8 个会话并发 followup：新 run 唯一、各会话只挂自己的两条 run |
| `test_concurrent_runs_with_redis_store` | 12 个 run 并发写 `RedisStore`：store 里 12 条、ID 不重复 |

跑法：

```powershell
.venv\Scripts\python.exe -m pytest tests/test_concurrency.py -q
```

### 2. 真实网络压测（手动）

`tools/loadtest.py` 在进程内起一个 uvicorn 服务（`InMemoryStore` 或指定 Redis），
用假 provider 并发打 HTTP 接口：

```powershell
# 200 个 run，100 并发，todo_write 工具（无子进程开销）
.venv\Scripts\python.exe tools\loadtest.py --runs 200 --concurrency 100 --tool todo_write

# 80 个 run，走 bash（每次都起 PowerShell，贴近真实工具开销）
.venv\Scripts\python.exe tools\loadtest.py --runs 80 --concurrency 40 --tool bash

# 用独立 Redis（别指向正在用的库）
.venv\Scripts\python.exe tools\loadtest.py --runs 100 --concurrency 50 --tool todo_write `
  --redis-url redis://127.0.0.1:6391/0
```

脚本会并发建 run、并发订阅 SSE（每条 run 一条流）、并发 followup，并输出：

- 建 run 的 p50 / p95 / max 延迟
- 全部 run 跑完的墙钟时间、失败数
- SSE 流数量、正常数、事件总数
- followup 成功数、会话数

## 实测结果

环境：Windows，Python 3.12.10，单进程 uvicorn，假 provider
（每个 run：2 次工具调用 + 1 次收尾，共 3 次模型调用），`max_steps=6`。

| 场景 | runs / 并发 | store | 工具 | 建 run p50 / p95 | 全部完成 | SSE | followup | error |
|---|---:|---|---|---:|---:|---:|---:|---:|
| 服务层开销 | 80 / 40 | InMemory | todo_write | 228 / 277 ms | 2.18 s | 80/80 流，640 事件 | 80/80，1.42 s | 0 |
| 服务层开销 | 200 / 100 | InMemory | todo_write | 434 / 519 ms | 5.39 s | 200/200 流，1600 事件 | 200/200，4.34 s | 0 |
| 带真实工具开销 | 80 / 40 | InMemory | bash | 906 / 1640 ms | 16.6 s | 80/80 流，640 事件 | 80/80，16.42 s | 0 |
| 持久化 store | 100 / 50 | Redis | todo_write | 438 / 509 ms | 4.11 s | 100/100 流，800 事件 | 100/100，3.09 s | 0 |

每条 run 的事件数都是 7（严格一致），没有丢事件。

## 怎么读这些数

- **bash 场景慢 7–8 倍，主要开销在工具，不在循环/store**：每次 bash 调用都要起一个 PowerShell 子进程。
  服务层本身在 200 并发、100 线程建 run 时，p50 约 434ms、p95 约 519ms。
- **SSE 没有串流**：每条流只收到自己的 8 个事件（start / model_call / tool_call ×2 / thinking / compact / finish / end 等），
  200 条并发流全部正常。
- **Redis 和 InMemory 在同样并发下建 run 延迟接近**（438 vs 434ms），Redis 多出来的主要是存储往返。
- **会话隔离**：80/200 个 run 对应 80/200 个会话，followup 都挂回自己的 root，没有串会话。

## 这个测试不覆盖什么

- **真实模型 API**：假 provider 没有网络延迟、限流、重试；这里量的是 harness 自身的并发能力。
- **多进程 / 多机**：单进程 uvicorn + 单 Redis；多副本需要看 Redis 竞争和负载均衡，不在当前范围。
- **前端渲染压力**：界面链路由 `web/uicheck.mjs` 覆盖，并发数据量下的浏览器渲染没在这里跑。
- **长任务内存增长**：`InMemoryStore` 默认最多留 200 条 run；高并发下要注意这个上限（RedisStore 用 TTL）。
